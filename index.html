Open a website and watch the trip.

When you enter a site name, the browser needs a destination IP address before it can start a new connection to that site. It first checks for a reusable address; otherwise it asks a DNS resolver.

  1. 01Enter a nameYou request example.com.
  2. 02Resolve it with DNSCache or resolver supplies an IP address.
  3. 03Connect securelyTCP with TLS, or QUIC, prepares transport.
  4. 04Request the pageHTTP asks for the document and resources.
  5. 05Process responsesThe browser receives and parses data.
  6. 06Render progressivelyContent becomes visible as work completes.

DNS happens before a new site connection: DNS means Domain Name System. Its query and answer are themselves packets that cross local links and routed networks. Chapters 1–6 unpack these foundations; Chapter 7 puts the browser events back into chronological order.

Chapter 03 / 08

Message, Meet Pieces

Goal: See why data travels in smaller pieces.

IP networks carry data in packets; on Wi-Fi or Ethernet, an IP packet rides inside a local-link frame. IP is best effort and does not recover every missing packet. When an application needs reliability, a transport such as TCP or QUIC can detect missing data, retransmit it, and deliver it in the required order.

Chapter 04 / 08

DNS: The Internet’s Name Game

Goal: See how the browser finds a destination address before opening a new site connection.

DNS—the Domain Name System—maps names people use to IP addresses networks can route toward. After you enter a site name, the browser and operating system check for a usable cached answer. If none is available, the device sends a DNS query to its configured resolver. The resolver can answer from its cache or perform more DNS lookups.

Where it happensAddress resolution happens before a new connection to the website. The DNS query and answer themselves use packets, local links, and routing.

Chapter 06 / 08

Secure Web Delivery: TCP + TLS and QUIC

Goal: Compare secure web transport over TCP and QUIC.

TCP provides a reliable, ordered byte stream. Web traffic commonly secures TCP with TLS. QUIC runs over UDP and integrates TLS 1.3 with its transport handshake while providing reliable delivery and independent streams. HTTP/3 uses QUIC; HTTP/1.1 and HTTP/2 commonly use TCP with TLS.

What about plain UDP?

UDP itself is a small, connectionless transport. An application can value timeliness over recovery or build additional behavior on top—as QUIC does.

Goal: Put the earlier concepts into the real order of a fresh website visit.

This is the chronological workflow. After you enter a name, a usable cached DNS answer can supply its IP address immediately; otherwise the device asks a DNS resolver. The browser can then create or reuse a secure connection, exchange HTTP data, process resources, and render progressively.
